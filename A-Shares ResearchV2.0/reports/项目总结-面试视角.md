# A股多智能体投研系统 —— 面试总结手册

> 讲述人身份：金融投研方向数据产品经理，有投研分析师经历，**不懂代码**，全程通过 AI Coding 主导本项目。

---

## 一、30秒电梯介绍（开场白，必须背熟）

> "我是一个有投研分析师背景的数据产品经理。我发现自己日常看一只股票要开七八个窗口——行情、财报、资金流、券商研报、估值分位——拼凑半天还缺角度。于是我设计并用 AI 编程落地了一套多智能体投研系统：7 个专业分析 Agent 像一个投研团队一样分工协作——技术面、基本面、资金面、行业面、估值面、风险面各自出结论，再由一个'首席 Agent'汇总成机构级报告，配上 8 种图表，还能基于报告继续追问。系统带自选股管理、机构研报自动拉取、事件时间线，以及最重要的——**判断力回测闭环**：历史每次判断都会在到期后用真实走势自动验证，统计胜率并反馈给下一次分析。这套系统我从产品定义、架构设计到质量验收全程负责，虽然我不写代码，但我建立了一套'AI 编码 + 人工验收'的工程化管理方法。"

## 二、3分钟完整版项目介绍（STAR结构）

### 1. 背景与痛点（为什么做）

个人投资者和初级分析师做一只股票的完整研究，存在三个结构性痛点：

| 痛点         | 具体表现                                  |
| ---------- | ------------------------------------- |
| **覆盖面靠自觉** | 看行情的人容易忽略基本面，看财报的人容易忽略资金面——六个维度很难每次都齐 |
| **结论不可追溯** | 今天判断"看多"，三个月后没人回来验证当时对不对，判断力永远得不到校准   |
| **信息分散低效** | 行情软件、公告、研报、资金数据散落在七八个终端，拼一份完整观点要好几个小时 |

### 2. 方案与产品形态（做了什么）

一套 Web 端投研工作台，核心是"**像管理一个投研团队一样管理 AI**"：

- **分析生产线**：输入股票代码 → 7 个维度 Agent 并行分析 → 多 Agent 互相审阅辩论 → 首席 Agent 汇总成结构化报告（评分 + 信号 + 风险 + 图表）
- **持续跟踪能力**：自选股管理、批量刷新快照、机构研报自动拉取（五层筛选漏斗：Top30 券商白名单 → 只留深度报告 → 180 天时效 → 自选股限定 → 每股最多 10 篇）、信号与风险自动写入事件时间线
- **判断力闭环**：每次分析的结论落库 → 到期后自动拉取真实价格验证方向对错 → 胜率统计注入下一次分析的上下文，让系统"知道自己历史上哪类判断容易错"
- **交互层**：三栏布局（自选股 / 分析区 / 对话面板），分析完成后可继续追问"估值合理吗？""主要风险是什么？"

### 3. 我的角色（负责人怎么讲）

> 关键话术："我不写代码，但我做三件事：**定架构、定标准、做验收**。"

- 定义业务架构：六个分析维度怎么切、信号怎么定级（7 级买卖信号：强买入→强卖出）、质量门槛怎么设
- 定义协作规则：AI 每完成一个改动，必须过单元测试 + 回测验证才算交付
- 主导技术债治理：组织了一次全量架构审计，发现 8 类问题，按优先级逐项推进清偿

### 4. 成果（数据背熟）

- 7 个专业 Agent + 首席 Agent + 数据 Agent 协同，覆盖 A股 + 港股 + 美股研报源
- 8 种可视化图表（K线/MACD/KDJ/RSI/雷达图/估值仪表/资金流向/杜邦分析）
- 技术债治理 8 项全部落地，单元测试从 28 个散装脚本重组为 **71 个规范用例，全部通过**
- 信号定级系统回测：33 笔历史交易，**胜率 57.6%**（覆盖 2026 年 1–6 月），显著高于主观散户基线
- 数据库迁移零丢失（79 条历史记录完整保留），并建立留存策略（每股 30 条 / 180 天自动清理）

## 三、架构怎么讲（不懂代码的讲法）

### 用"投研团队"类比，面试官秒懂

> "我把它设计成一家小型研究所：**6 个行业研究员**（技术、基本面、资金、行业、估值、风险各管一摊）、**1 个首席**（汇总成报告）、**1 个数据中台**（所有数据只有一个进口）。"

### 三层架构 = 制度设计（这是产品经理的亮点）

系统分三层，每层是一条"铁律"：

| 层                  | 类比        | 铁律（为什么这么设计）                                     |
| ------------------ | --------- | ----------------------------------------------- |
| **Skills 计算层**     | 研究员的方法论手册 | 纯计算规则，**不允许 AI 自由发挥**——指标算出来是多少就是多少，杜绝大模型"编数字"  |
| **Connectors 数据层** | 所里的数据中台   | 全系统**唯一数据进口**——数据从几个源进来、什么口径，只在一个地方把关，避免各维度各说各话 |
| **Agents 执行层**     | 研究员本身     | 只负责调用方法论 + 数据 + 组织语言，**不碰底层数据**                 |

> 面试加分句："这个分层的本质是**把'可信的'和'有创造性的'分开**——计算交给规则，语言交给大模型。这是我在投研行业养成的直觉：数据口径必须唯一，观点可以多元。"

### 一句话讲数据流转

> "数据从中台进来 → 算法层算出客观指标 → 各维度 Agent 结合数据写各自的分析 → 互相审阅辩论一轮 → 首席 Agent 汇总打分、定信号 → 落库存档 → 到期回测验证。"

## 四、AI Coding 遇到的问题与解决思路（面试核心弹药）

这一部分分两类：**AI 生成代码的工程问题** 和 **人机协作的管理问题**。每条都是真实发生过的案例，按"现象 → 根因 → 解决 → 启示"来讲。

### 4.1 AI 生成代码的六大工程问题

#### 案例一：同一件事写了八遍——重复调用没有治理

- **现象**：大模型调用的代码在 8 个地方各自手写，没有超时、没有重试、没有用量统计。网络一抖整个分析就挂。
- **根因**：AI 是"逐次任务式"生成代码的——每次让它加一个功能，它就地写一份调用，没有全局视野去复用。
- **解决**：要求建一个**统一调用层**：重试（只对网络类瞬态错误重试 3 次、指数退避）、超时、用量统计全部收口到一处，然后把 9 处手写调用全部替换过去。
- **启示话术**："AI 编码最大的隐患不是写不出功能，而是**每次都给你重写一遍**。治理方法是要求它'先建制度再干活'——公共能力必须收口到单一出口。"

#### 案例二：六个 Agent 复制粘贴——样板代码堆积

- **现象**：6 个分析 Agent 各自携带一份几乎一样的流程代码（取数→计算→组织提示词→调用模型→解析结果），改一个流程要改六处。
- **根因**：同一个道理——AI 没有主动抽象的动力，它优先保证"当前这个能跑"。
- **解决**：把公共流程抽成一个**基础模板**，6 个 Agent 只保留各自的差异化部分（取什么数、算什么指标、怎么提问）。
- **启示话术**："我把这理解为'团队里每个人都在抄同事的周报模板'。解法不是骂人，是把模板统一收归管理。"

#### 案例三：两个用户互相覆盖——并发串台

- **现象**：两个浏览器标签页同时分析不同股票，会出现结果互相覆盖、状态错乱。
- **根因**：AI 写代码时图省事，把核心调度器做成了**全局唯一实例**，所有请求共享同一块"草稿纸"。单人用没问题，两人同时用就互相涂改。
- **解决**：改为**每次请求一张独立草稿纸**，会话之间完全隔离；对话功能也补上会话隔离，多用户不串台。
- **启示话术**："这类问题 AI 自己测不出来——它默认你在单人使用。所以产品经理必须把**使用场景**讲清楚：几个人用、同时用还是排队用。这是业务方定义需求的责任，不能指望 AI 替你想。"

#### 案例四：ROE 差了 100 倍——数据口径灾难（最有讲头的案例）

- **现象**：审查时发现同一指标在不同路径下的口径不统一：有的地方 ROE 存成 0.105，有的存成 10.5——**相差 100 倍**。这种数据直接喂给大模型，分析结论全错，而且表面上完全看不出来。
- **根因**：不同数据源返回的格式五花八门（带百分号/不带、单位是亿/万/元），AI 在每个取数点就地"顺手处理"了一下，处理规则不一致。
- **解决**：在**数据中台的唯一进口处**统一量纲规则（百分比统一 0-100、金额统一到元），并配字段级单元测试（"10.5%"必须变成 10.5，"1.5万亿"必须变成 1.5×10¹²）。
- **启示话术**："这是我最警惕的一类问题——**静默的错误**。系统不报错、报告照常生成，但数字是错的。我在投研行业的经验是：数据口径必须在入口统一，出了入口就晚了。所以我坚持所有数据只有一个进口。"

#### 案例五：一本账记了两遍——数据双写

- **现象**：同一个分析结果存在两张表里重复记录，还发现一个完全没人用的"孤儿数据库"。数据会失去同步，且无限膨胀。
- **根因**：功能是分多次让 AI 加的，每次加功能它就近建了个新表，没有全局数据模型。
- **解决**：合并成**单一记录表 + 一次性迁移**（79 条历史记录零丢失），并补上留存策略：每股最多 30 条、超过 180 天自动清理。
- **启示话术**："这相当于公司有两套账本，迟早对不上。治理动作是'并账 + 设销毁规则'。"

#### 案例六：名存实亡的功能——断点续跑从未生效

- **现象**：宣传里有"断点续跑"能力，审计发现它写的会话标识每次都是新时间戳，恢复入口根本没人调用——**这功能从来没真正跑过**；另有整目录的废弃代码、32 个约 40MB 的孤儿文件堆积在仓库里。
- **根因**：AI 会顺着你的话把功能"写出来"，但不保证它被真正接入主流程；而没人用的代码它也不会主动清理。
- **解决**：我的原则是"**做实或删除，不允许薛定谔的功能**"——评估后续确实用不上，就把断点续跑整个删除（40MB 垃圾清空），并约定将来真需要时再按新方案重建；同类废弃模块一并清退。
- **启示话术**："AI 时代的技术债有个新形态：**它把'承诺的功能'和'兑现的功能'混在一起交付**。验收标准必须是'端到端跑通'，而不是'代码存在'。"

### 4.2 人机协作的管理问题（PM 方法论，最出彩的部分）

#### 问题一：AI 说"修好了"，但根本没修好——用回测验收

- **现象**：让 AI 修复一个信号定级规则（MA60 方向约束），它报告"修改完成、测试全过"。但回测结果与修改前**完全一致**——一个字节都没变。
- **解决思路**：这反而证明根因判断错了——修的不是病根。于是不采纳这次修复结论，退回去从第一性原理重新排查（最终确认真正吞没信号的是得分门槛环节，而非方向约束）。
- **话术**："我不接受 AI 的自我汇报，**只接受数据验收**。所有改动必须过'回测对比'：改了之后结果应该变化，如果纹丝不动，要么改错了地方，要么改了个死代码——两种情况都必须停下重查。"

#### 问题二：我不懂代码，怎么提需求、怎么定位问题？

- **方法**：用**业务现象**描述问题，而不是用技术语言。例如：不说"序列化类型错误"，而说"页面上点分析按钮直接报 500，日志显示是某个布尔值存不进 JSON"；不说"状态共享竞态"，而说"两个标签页同时分析会互相覆盖"。
- 然后要求 AI **从第一性原理排查**："先别急着改，先帮我检查，把表象一步步追到根源，讲给我听。" AI 负责下钻，我负责判断逻辑是否自洽——**业务逻辑对不对，产品经理是看得懂的**。
- **话术**："我不需要看懂每一行代码，但**每一个根因解释必须在业务逻辑上说得通**。说'因为共享了状态所以互相覆盖'，我听得懂；说不清业务因果的修复方案，我一律不批。"

#### 问题三：改动一发动全身——回归风险怎么控？

- **方法**：把全仓 28 个散装测试脚本重组为规范测试体系，**71 个单元测试作为每次交付的强制门槛**；不依赖网络的测试归入默认回归，联网测试单独隔离。每次修改后先跑全量测试，再跑回测对比，双保险后才算交付。
- **话术**："相当于上线前的 UAT 清单。我不看代码 diff，我看测试报告和回测数字。"

#### 问题四：AI 记不住全局——用"先审计、再排序、后执行"管住它

- **现象**：功能是一个个加出来的，AI 每次只看到眼前任务，导致重复代码、双份数据、死代码越积越多。
- **方法**：先做一次**全量架构审计**（8 大类问题一次性摸清），排出优先级清单，然后**严格按编号逐项推进**：统一调用层 → 并发修复 → 模板化 → 数据库合并 → 死功能处置 → 口径统一 → 清理+测试体系 → 回测接入主链路。每完成一项，验证、文档化，再进下一项。
- **话术**："这本质是项目管理问题，不是编程问题。AI 是最好的执行者、最差的架构师——**架构和优先级必须由人拍板**。"

#### 问题五：细节环境坑——AI 也会栽在小坑里

- **现象**：Windows 下一个启动脚本连错两次，根因是编码和换行符这类"上古问题"（批处理必须 CRLF 换行、含中文路径必须带 BOM 编码）。
- **解决**：让 AI 复盘失败原因并**把结论固化成文档经验**，下次同类问题不再踩。
- **话术**："AI 的知识是通用的，你的环境是具体的。这类坑要靠'踩一次、记一条'的沉淀机制消化。"

## 六、面试 Q\&A 预演

**Q1：你不懂代码，怎么保证 AI 写的系统是对的？**

> "三道防线。第一道是**架构防线**——计算规则和语言生成分离，指标全部由确定性规则算出，AI 只负责组织观点，它编不了数字。第二道是**测试防线**——71 个单元测试是强制门槛，不过不许交付。第三道是**数据防线**——所有历史判断到期自动回测，胜率摆在那里，这个系统好不好，市场说了算，不是我说了算。"

**Q2：AI coding 和传统开发比，最大的坑是什么？**

> "传统开发的坑是'写得慢'，AI coding 的坑是'**写得快但欠账快**'。AI 没有全局视野，每个任务都就地最优，重复代码、双份数据、名存实亡的功能会静默累积。我的对策是把 AI 当成一个能力很强但没有记忆、没有全局观的执行团队来管理：定期架构审计、按优先级排期、每项验收后归档。"

**Q3：项目里遇到的最难的问题？**

> 讲 ROE 100 倍口径案例（4.1 案例四）+ 收尾："最危险的问题不是报错，而是不报错。数据口径问题表面无恙、结论全错，而且会污染大模型的输入。这件事之后我把'唯一数据进口 + 入口统一量纲'定为系统铁律。"

**Q4：怎么发现并发串台这种自己测不出来的问题？**

> "场景思维。AI 默认单人使用，但产品定义是我给的——我就问它：两个用户同时分析会怎样？它顺着这个问题去查，才发现共享状态的缺陷。**产品经理的价值就在这里：把使用场景讲清楚，是业务方的责任。**"

**Q5：回测闭环是怎么设计的？**

> "每次分析落库时记下当时的价格、评级、信号。到期后系统自动拉真实走势验证方向对错，统计维度级胜率，再把校准结论注入下一次分析的上下文——相当于给每个研究员发一张历史成绩单。目前 33 笔样本、57.6% 胜率，样本还小，但闭环已经跑通，数据会自己积累。"

**Q6：如果重来一次，你会怎么改进？**

> "三条：一是**先定数据契约再写功能**——100 倍口径问题本质上是最该在第一天就锁死的；二是**测试体系先于功能**——前 60% 的时间没有测试门槛，欠了很多回归债；三是更早引入审计，技术债发现得越晚，清偿成本越高。"

**Q7：这个项目和市面上的 AI 投资工具有什么区别？**

> "两点。第一，多数工具是'一个大模型直接回答'，我是**多角色分工+互相辩论+确定性计算**——观点可以多元，数字必须唯一。第二，也是我认为最有价值的：**判断力校准闭环**。别家告诉你'买'，没有一家会回头统计自己说了多少次买、对了多少次。我的系统会。"

**Q8：多智能体为什么要这么设计？会不会很浪费？**

> "分工的收益是覆盖完整和互相制衡——六个维度一个都不漏，而且分析之间会交叉审阅，防止单一视角的偏见。成本上做了工程控制：统一调用层的重试/超时/用量统计、并行调度、按维度拆分控制每次调用的规模。"

**Q9：项目后续规划是什么？**

> "从'一次性分析工具'进化为'持续跟踪、可复盘、自我校准的系统'：每日自动化刷新+到期回测、单股→组合管理（行业集中度/仓位风控）、历史胜率注入分析上下文的深度校准、以及'我 vs 券商 vs 市场'的对决复盘。"

**Q10：不懂代码却主导工程化项目，你的底气来自哪里？**

> "我对两件事负责：**业务逻辑对不对，验收标准严不严**。架构上'计算与观点分离'是我从投研行业带来的原则；每一个修复方案我都要求 AI 讲到业务因果层面让我复核；每一次交付都拿测试报告和回测数字说话。代码是 AI 写的，但系统的方法论和质量标准是我的。"
